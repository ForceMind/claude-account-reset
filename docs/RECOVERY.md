# 换账号后恢复本地 Code 会话

## 数据未删除，也可能看不到

Desktop 的会话索引通常按账号及组织目录存放，而 Code 的主会话正文位于默认 `~/.claude/projects/<project>/<session-id>.jsonl`。换账号后，原目录及正文可能都在，但新账号的列表没有对应索引。

这与“恢复已删除的数据”不同：工具依赖现存正文，不能从缺失文件制造历史。也不能把普通云端聊天迁入新账号。

## 本次经验如何进入工具

一次受控的本地恢复中，50 条不同 Code 会话都找到了对应正文。原件保留，为新账号新建最小本地索引；4 条原归档记录保持归档，1 条工作目录缺失被单独报告。重开客户端后看到列表，并抽查了一条正文正常显示。

这是手工流程的验证范围，**不是批量发送消息或跨组织推理兼容性的验收**。0.2.0 将该机制抽象为独立命令，使用合成数据覆盖去重、冲突、目标歧义和失败处理，不再次操作原用户的真实数据。真实路径、账号、会话内容和备份不发布。

本次检查未找到可恢复的 Cowork 会话正文，所以工具不宣称支持 Cowork；用量账本、定时任务和设置文件不能当作聊天正文。

## 为什么不直接复制整个旧账号目录

旧索引可能带有云端桥接 ID、连接器配置、远程控制或待执行动作。工具只保留允许清单内的本地展示、时间、路径和会话标识字段，不复制这些关联；权限设为手动，远程控制关闭。它不替换当前登录配置，也不修改正文中的用户消息、回答、工具记录和 thinking。

源索引按 CLI 会话 ID 去重，已有目标记录优先。相同正文 ID 对应多个不同内容的文件时，工具报告歧义并跳过。组织目录不唯一时要求 `--org`，不自动猜测。

## thinking 的组织绑定不是登录残留

用户实际继续对话时，客户端提示 `Claude can't use thinking from another organization`。这暴露了一个必须明确的边界：**能够看到旧历史，不意味着新账号能复用全部旧推理。**

[官方 preserved thinking 文档](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking#thinking-blocks-stay-with-the-account-that-produced-them)说明，部分模型生成的 thinking 绑定产生它的账号，跨组织使用时可能被丢弃，请求仍可成功。新的回答需要重新推理，可能消耗更多 token 和时间。

0.2.0 的处理策略是：

1. 读取 JSONL 中 assistant message 的内容块，仅统计 `thinking`、`redacted_thinking` 和存在 signature 的块。
2. 不打印推理文本、签名或密文；不解密签名，不从计数推断具体组织。
3. 在预览及执行报告中明确 `policy: preserve`、`organizationCompatibility: not-verified`。
4. 保留完整历史，不删除或伪造签名，不尝试绕过组织绑定。已恢复的会话重复预览时也会重新检测 thinking。

如未来需要“去 thinking 的迁移副本”，它应是另一个明确授权、保留原件的转换流程，不能偷偷合并到清理或恢复中。官方文档也指出只删中间部分思考可能破坏后续块的关联，因此不能用简单字符串替换处理。

## 执行、验证和失败

预览阶段读取配置、索引、正文并计算必要的哈希，不创建备份或索引。执行阶段先确认客户端关闭、目标账号未变，再私有备份目标目录；新增文件使用独占创建，拒绝覆盖。

每次写入更新本地 manifest。完成后回读新增记录，核对已有源/目标索引及相关正文的哈希。受控失败会尝试删除本次新建记录，保留原件与备份。异常断电或回退失败需要检查 manifest，不应整目录覆盖目标中后来产生的新对话。

报告成功只表示索引与保护检查完成。命令不会启动客户端、发送测试提示词或自动验收模型回复；`uiVerified` 保持 false。使用者应重开 Claude 检查显示情况，并独立确认继续工作的路径和组织策略。

## 0.3.0 的独立转换选项

`recover.mjs` 继续保留 thinking。需要清理已知思考并生成可见历史接手文档时，使用 [HANDOFF.md](HANDOFF.md) 中的独立命令。它会改写正文，需要显式确认，不能当作只恢复列表的一部分偷偷执行。
